# AUTH.md — вход и защита данных

## Как это устроено (простыми словами)

1. Сайт закрыт **Cloudflare Access**: прежде чем открыть любую страницу, Cloudflare просит ввести почту и присылает на неё одноразовый код. Пароль придумывать и хранить не нужно.
2. Когда сайт обращается к своему серверу (адреса `/api/...`), Cloudflare добавляет в запрос «пропуск» (заголовок `Cf-Access-Jwt-Assertion`).
3. Наш сервер (Worker) **сам проверяет пропуск**: подпись Cloudflare, адрес вашей команды Zero Trust, метку приложения (AUD) и срок действия. Наличия заголовка или адреса почты недостаточно.
4. Затем проверяется, что почта есть в списке `ALLOWED_EMAILS`. Это вторая, независимая защита.
5. Любая ошибка настройки закрывает дверь: без настроек сервер отвечает ошибкой, а не пускает всех.
6. Запросы на запись принимаются только со страниц самого сайта и только в формате JSON (защита от подделанных запросов с чужих сайтов).

Пользователь определяется на сервере по проверенному пропуску. Идентификатору, который присылает браузер, сервер не доверяет.

## Что нужно сделать в Cloudflare (один раз)

Названия кнопок в панели Cloudflare иногда меняются; если пункта нет на месте, ищите рядом похожий и пришлите мне скриншот.

### Шаг 1. Правило «только я» (политика Access)

1. Откройте Cloudflare Dashboard → **Zero Trust** (или Cloudflare One).
2. Слева **Access controls** → **Policies** → **Add a policy**.
3. Название: `Owner only`. Действие (Action): **Allow**.
4. В блоке **Include** выберите **Emails** и впишите свою почту, на которую придёт код входа.
5. Сохраните (**Save**).

Не выбирайте вариант «Email domain: gmail.com»: он пустил бы любого человека с адресом gmail.

### Шаг 2. Закрыть сайт входом

1. Dashboard → **Workers & Pages** → ваш проект (Worker) → вкладка **Access**.
2. Нажмите **Protect this Worker behind Access** и выберите **All traffic** (весь сайт, а не только предпросмотры).
3. В качестве политики выберите созданную `Owner only` (не «Email domain»).
4. Сохраните.

### Шаг 3. Скопировать два значения

1. **Адрес команды (team domain)**: Zero Trust → **Settings** → **General**. Он выглядит как `https://имя.cloudflareaccess.com`.
2. **Метка приложения (AUD tag)**: Zero Trust → **Access controls** → **Applications** → приложение вашего Worker → **Edit** → **Additional settings** → **Application Audience (AUD) Tag**. Это длинная строка из букв и цифр.

### Шаг 4. Записать их в Worker как секреты

Dashboard → **Workers & Pages** → ваш Worker → **Settings** → **Variables and Secrets** → **Add**. Тип (Type) обязательно **Secret**:

| Имя | Значение |
|---|---|
| `TEAM_DOMAIN` | адрес команды из шага 3 |
| `POLICY_AUD` | метка приложения из шага 3 |
| `ALLOWED_EMAILS` | ваша почта (если несколько, через запятую) |

Нажмите **Deploy**. Секреты хранятся в Cloudflare, а не в GitHub, и не пропадают при следующих публикациях сайта. Ваша почта в GitHub нигде не попадает.

### Шаг 5. Проверка

1. Откройте сайт в окне инкогнито. Должна появиться страница входа Cloudflare. Введите почту, из письма введите код, сайт откроется.
2. Откройте `адрес-сайта/api/me`. Должен показаться JSON с вашей почтой, например `{"email":"...","source":"access"}`.
3. Откройте `адрес-сайта/api/health`: `{"ok":true,...,"database":"not_configured"}` (базу подключим позже).
4. Попробуйте войти другой почтой (не из списка): доступ должен быть закрыт.

### Как отключить, если что-то пошло не так

Workers & Pages → ваш Worker → **Access** → отключить защиту. Или откатить последний коммит в GitHub.

## Локальная разработка

Файл `.dev.vars` (его нет в GitHub) на вашем компьютере:

```
ALLOW_DEV_AUTH=true
DEV_AUTH_EMAIL=you@example.com
```

Такой вход работает **только** при трёх условиях одновременно: флаг включён, указана почта и запрос идёт на `localhost`. На рабочем сайте этой переменной нет, а на настоящий адрес сайта такой вход не действует вообще (проверено автоматическим тестом). Образец: `.dev.vars.example`.

## Что проверяют автоматические тесты

`tests/auth.test.ts` и `tests/security.test.ts` создают настоящие RSA-ключи и подписывают пропуска так же, как Cloudflare. Проверяется:

- настоящий пропуск принимается;
- чужой ключ, изменённая подпись, алгоритмы `none` и HS256, чужая команда, чужая метка приложения, истёкший срок, пропуск без почты отклоняются;
- ключи скачиваются один раз, обновляются при смене ключа и не могут вызвать бесконечные загрузки;
- без настроек, без пропуска, с чужой почтой, при недоступных ключах сервер отвечает ошибкой, а не пускает;
- вход для разработчика не открывает рабочий сайт;
- запросы с чужих сайтов и не в формате JSON отклоняются, размер тела ограничен.
