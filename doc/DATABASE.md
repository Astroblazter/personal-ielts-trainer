# DATABASE.md — база данных Cloudflare D1

Этот документ описывает облачную базу IELTS Trainer: какие в ней таблицы, как они связаны с тем, что сайт хранит сейчас в браузере, по каким правилам идёт синхронизация и как применять миграции.

Состояние: проект базы данных (этап 2). Сами API и синхронизация будут добавлены на следующих этапах, поэтому разделы «Синхронизация» и «Перенос» описывают принятые правила, а не готовый код.

## 1. Главные принципы

1. **Каждая запись принадлежит пользователю.** У всех таблиц с данными ученика есть `user_id`. Первичный ключ всегда `(user_id, id)`: идентификатор записи уникален только внутри одного пользователя, поэтому даже при ошибке в коде один пользователь не может перезаписать чужую строку.
2. **Пользователь определяется на сервере** по проверенному входу через Cloudflare Access, а не по тому, что прислал браузер (этап 3).
3. **Идентификаторы** — текст. Записи, созданные до облака, сохраняют старые номера (`att-…`, `mis-…`, `v-001`). Новые записи получают UUID, созданный в браузере.
4. **Время** — целое число миллисекунд от 1970-01-01 в UTC (то, что сайт уже использует). Дата дня обучения (`local_date`) хранится отдельно как текст `ГГГГ-ММ-ДД` по местному времени ученика.
5. **Добавление, а не перезапись:** ответы, занятия, результаты диагностики и тестов только добавляются. Изменяемые сущности (слова, ошибки, настройки) обновляются по правилу «побеждает более новая версия».
6. **Удаление мягкое** для слов и ошибок (`deleted_at`): так другие устройства узнают об удалении.
7. **Повторная отправка безопасна:** одна и та же запись, отправленная дважды, не создаёт дубликата (составной первичный ключ плюс `ON CONFLICT`).
8. **Нестрогие типы SQLite дополнены проверками** (`CHECK`): перечисления, диапазоны, длина текстов, корректность JSON. Неправильное значение отклоняет сама база.

## 2. Таблицы

### Пользователи и устройства

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Владелец данных | `id`, `email` (строчными буквами, уникальный), `access_sub` (постоянный номер из Cloudflare Access), `status` (`active` / `blocked`), `created_at`, `last_seen_at` |
| `devices` | Устройства (браузеры) пользователя | `(user_id, id)`, `label`, `first_seen_at`, `last_seen_at`, `last_pull_seq` (до какого номера журнала устройство уже прочитало изменения) |

### Настройки

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `user_settings` | Настройки и профиль одной строкой на пользователя | `theme`, `interface_language`, `daily_goal_minutes`, `target_ielts_score`, `current_level`, `last_diagnostic_at`, `updated_at`, `version` |

В браузере цель по минутам и целевой балл сейчас лежат в двух местах (настройки и профиль). В облаке они в одном месте: главным считается значение из настроек, из профиля берутся только уровень и дата диагностики.

### Занятия и результаты

| Таблица | Назначение | Ключевые поля | Индексы |
|---|---|---|---|
| `attempts` | Каждый ответ на упражнение | `exercise_id`, `topic_id`, `type`, `correct`, `user_answer`, `suggested_correction`, `time_spent_ms`, `source`, `created_at`, `updated_at` | по `(user_id, created_at)`, `(user_id, exercise_id, created_at)`, `(user_id, topic_id, created_at)` |
| `mistakes` | Журнал ошибок с расписанием повторений | `exercise_id`, `category`, `status` (`active` / `understood` / `archived`), `attempts`, `next_review_at`, `review_interval_days`, `deleted_at` | уникальный: одна открытая ошибка на упражнение; по `(user_id, status, next_review_at)` |
| `vocabulary_words` | Словарь | `word`, `translation_ru`, `example_en`, `theme`, `difficulty`, `stage` (0–5), `review_status`, `correct_count`, `incorrect_count`, `next_review_at`, `deleted_at` | по `next_review_at`, по `theme` |
| `study_sessions` | Завершённые занятия | `local_date`, `kind`, `exercises_completed`, `correct_count`, `time_spent_ms` | по `(user_id, local_date)` |
| `diagnostic_results` | Результаты диагностики | `taken_at`, `total_questions`, `correct_count`, `per_topic` (JSON), `estimated_level`, `level_score` | по `(user_id, taken_at)` |
| `lesson_states` | Незаконченный урок дня (одна строка на день) | `exercise_ids` (JSON), `current_index`, `answers` (JSON), `completed_at` | — |

`study_sessions`: сейчас сайт хранит **одну суммирующую запись на дату**. Два устройства создали бы записи с одним ключом и разными числами, поэтому в облаке каждое занятие — отдельная строка (`kind` показывает, что это было: урок дня, чтение, пробный экзамен и т. д.), а сумма за день считается при чтении. Дни из старой версии переносятся как по одной строке на дату: `kind = 'legacy_day'`, `id = 'legacy-day-ГГГГ-ММ-ДД'`.

### Чтение, аудирование, письмо, говорение, пробный экзамен

Эти результаты сайт **раньше не сохранял вообще**, в облаке они сохраняются с первого дня.

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `section_results` | Один выполненный текст, запись, задание или карточка | `section` (`reading` / `listening` / `writing` / `speaking`), `content_id`, `mock_exam_id` (если это часть пробного экзамена), `score`, `max_score`, `time_spent_ms`, `word_count`, `text_answer` (сочинение или письмо), `details` (JSON) |
| `mock_exams` | Один пробный экзамен целиком | `taken_at`, `time_spent_ms`, `total_score`, `total_max`, `sections` (JSON) |

Что лежит в `details` (JSON):

- чтение и аудирование: `{ "answers": { "<номер вопроса>": { "answer": "…", "correct": true } } }`;
- письмо: `{ "checklist": ["wc1", "wc3"], "selfScore": 4 }`, а сам текст в `text_answer`, число слов в `word_count`;
- говорение: `{ "recorded": true, "recordingSeconds": 63 }`.

**Аудиозаписи не сохраняются.** Страница «Говорение» обещает, что запись остаётся только в вашем браузере и никуда не отправляется; это обещание сохранено. В облако уходят только факты: какая карточка, сколько секунд, отмечено ли выполнение. Если позже понадобится хранить записи, для этого нужно отдельное хранилище файлов, это отдельное решение.

### Синхронизация и перенос

| Таблица | Назначение |
|---|---|
| `sync_log` | Журнал изменений: каждая применённая запись добавляет строку (`seq` только растёт). Устройство помнит последний прочитанный `seq` и запрашивает более новые |
| `sync_conflicts` | Проигравшая версия при конфликте сохраняется здесь, а не пропадает молча |
| `import_runs` | Итог разового переноса данных из браузера: сколько найдено и сколько оказалось в базе, список пропущенных записей с причиной, подтверждение резервной копии |

Уникальный индекс не даёт записать один и тот же набор данных как успешно перенесённый дважды (по `fingerprint` — хэшу экспортированных данных). Прерванный перенос можно повторить.

## 4. Правила синхронизации (принятые решения)

1. **Порядок записи:** изменение сначала надёжно сохраняется в браузере и ставится в очередь отправки, затем уходит на сервер. Без интернета очередь ждёт.
2. **Добавляемые записи** (ответы, занятия, результаты): если запись с таким номером уже есть, второе добавление ничего не меняет.
3. **Изменяемые записи** (слова, ошибки, настройки): применяется версия с более поздним `updated_at`. Версия, пришедшая с меньшим временем, не применяется и сохраняется в `sync_conflicts`. При каждом применённом изменении `version` увеличивается на 1.
4. **Защита от неверных часов:** время изменения, которое сервер получил из будущего больше чем на 5 минут, он сдвигает к текущему времени, чтобы устройство с неправильными часами не «выигрывало» всегда.
5. **Одна открытая ошибка на упражнение:** если два устройства создали ошибку по одному упражнению, второе добавление отклоняется с указанием уже существующей записи, и устройство сливает их у себя.
6. **Удаления** передаются как `deleted_at`; настоящее удаление строк не используется.
7. **Массовое удаление** (например, «импорт с заменой» в старой версии) в синхронизацию как удаление всего не уходит: оно требует отдельного подтверждения (этап 5–7).

## 5. Правила очистки данных при переносе

Старые данные могут содержать значения, которые база отклонит. Перенос не обрывается: проблемная запись исправляется или пропускается, а причина попадает в `import_runs.skipped` и показывается вам.

- `timeSpentMs` вне диапазона 0–24 часа (в одной из ранних версий время считалось от начала всего урока): ставится 0.
- Слишком длинный текст ответа: обрезается до 4000 знаков (в отчёте пометка).
- Неизвестное значение категории, сложности, темы: заменяется значением по умолчанию (`other`, `B1`, без темы).
- Нет даты изменения: берётся дата создания.
- Две открытые ошибки по одному упражнению: остаётся более новая, остальные пропускаются с причиной.
- Нет номера записи: запись пропускается.

## 6. Лимиты Cloudflare D1 (по официальной документации)

| Параметр | Бесплатный тариф |
|---|---|
| Строк прочитано в сутки | 5 млн |
| Строк записано в сутки | 100 тыс. |
| Хранилище в аккаунте | 5 ГБ, до 500 МБ на базу |
| Восстановление Time Travel | 7 дней (на платном тарифе 30) |

Для одного ученика это очень большой запас. Актуальные цифры проверяйте на страницах Limits и Pricing у Cloudflare.

## 7. Миграции

Каждое изменение структуры базы — отдельный пронумерованный SQL-файл в папке `migrations/`:

```
migrations/0001_initial_schema.sql    — начальная структура
migrations/0002_<название>.sql        — следующие изменения
```

Правила:

1. **Применённые файлы не редактируются.** Любое изменение — новый файл со следующим номером.
2. Нумерация без пропусков, имя вида `0002_add_something.sql` (проверяется автоматическим тестом).
3. В файлах нельзя использовать `BEGIN`, `COMMIT` и `PRAGMA`: Cloudflare управляет транзакциями сам (проверяется тестом).
4. Изменения лучше делать добавляющими (новая таблица, новый столбец с `DEFAULT`), не стирая данные.
5. Перед применением на рабочей базе мигрировать сначала тестовую (раздел о тестовой базе будет в DEPLOYMENT.md).

Команды (точные значения и порядок шагов будут в DEPLOYMENT.md после создания базы; название базы и `database_id` вы получите при её создании в Cloudflare, выдумывать их нельзя):

```
npx wrangler d1 migrations list <название_базы> --local
npx wrangler d1 migrations apply <название_базы> --local     # тестовая локальная база
npx wrangler d1 migrations apply <название_базы> --remote    # рабочая база
npx wrangler d1 migrations create <название_базы> add_something   # создаёт 0002_add_something.sql
```

Cloudflare сам ведёт таблицу `d1_migrations` со списком применённых файлов: это и есть версия структуры базы.

## 8. Как проверяется схема

Файл `tests/migrations.test.ts` применяет настоящие миграции к пустой базе SQLite и проверяет, в том числе:

- набор таблиц и индексов;
- что у каждой таблицы есть владелец и каскадное удаление, а ключ содержит `user_id`;
- отклонение неверных значений;
- изоляцию пользователей;
- одну открытую ошибку на упражнение;
- безопасность повторной отправки и правило «побеждает более новое»;
- журнал изменений и защиту от повторного переноса того же набора данных.

Запуск: `npm test` (нужен Node 22.13 или новее; на старых версиях эти тесты пропускаются).
